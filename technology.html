DetectLab documentation

The technology behind DetectLab

Five modules work together: the APM 2.0 archaeological prediction model, the multi-source agent Library of Babel, the archaeological potential zones, the LIDAR Scanner — built on a machine-learning process — and the archaeological report. This page explains what each one is, which data it uses and how to read its output.

DetectLab is not a map of “treasure spots”. It is a spatial analysis system that overlays environmental data, heritage registers, documentary corpora and LiDAR-derived models, then scores them. Every result shown has a reason: an environmental factor, a distance to known sites, a LiDAR detection or a documentary mention.

This page describes the instruments. The Process page describes the workflow — how they connect, in which order, with which thresholds, and what you get at the end.

1. Platform architecture

Each module can be used on its own, but the value appears when the results are overlaid. The archaeological potential zones, for instance, feed the archaeological report; objectives validated by the LIDAR Scanner can automatically raise a report location's score; the Library of Babel tells you which epochs are documented in that locality.

2. APM 2.0 — the archaeological prediction model

The APM (Archaeological Prediction Model) is a probability raster: for every patch of land, the model computes how likely that area is to have been settled or used in the past. It does not verify what is buried there — it measures how well the terrain matches the known patterns of old settlements.

What the model reads

  • Terrain: elevation, slope, aspect, position on the hillside (terraces, promontories, sheltered valleys).
  • Hydrography: distance to rivers, springs and wetlands — water explains most site locations.
  • Geology and soils: fertility, substrate stability, mineral and building resources.
  • Built-up mask (UAT): separates open land from built-up areas, so the model does not “predict” inside yards and streets.

The score and its legend classes

The layers are combined with weights in QGIS, and the result is published as raster tiles over the satellite imagery. The legend colours match the classes the other modules use:

How to read it correctly: the colour describes the terrain, not an object. A blue area means “the conditions here resemble the known settlements best”, not “there is a site here”.

3. Library of Babel — the documentary corpus of a locality

The Library of Babel is a multi-source search agent. You type a locality or a site (for example Sarmizegetusa, Apulum, Grădiștea Muncelului) and the agent queries 9 open sources at once, aggregates the results, removes duplicates and renders them with per-source provenance. The search runs directly in the browser, in Romanian and English.

Before querying the sources, the name is resolved against the OpenStreetMap gazetteer: the agent picks up the canonical name (with diacritics), the county and the coordinates, and the text sources receive the name as an exact phrase — otherwise an engine searching for “Miluani” would return “Miljan Miljanić”.

ARIADNE — why the query is never sent as typed. The portal's engine matches whole tokens and does not fold diacritics: its type-ahead already offers the record at “Moldovene” (it appends a wildcard), yet the results page answers “No resources found” for the complete, diacritics-free “Moldovenesti”, while “Moldovenești” returns 36 records and “Moldovene*” returns 81. The agent therefore repairs the query: it sends the canonical gazetteer spelling (accented), a wildcard stem cut in front of the last diacritic (“Moldovene*”) and the user's own spelling, then merges the answers by resource id. Hits coming from the widened variants are kept only when the record really mentions the locality, so “Moldoveni” (Ialomița) never lands in the corpus of “Moldovenești” (Cluj).

When the same finding appears in several sources (“Ulpia Traiana Sarmizegetusa” in Wikipedia, Wikidata and DBpedia, say), it becomes a single card with badges for every contributing source and a relevance score that favours findings confirmed by multiple sources. The statistics show how many duplicates were removed and how many results were rejected as irrelevant.

If one source does not answer, the others carry on: each source has a status chip naming the failure (timeout / HTTP / network / missing API key). Zero results always come with alternative-search suggestions, and an ambiguous locality (several OSM matches) is shown as a list of variants instead of being silently picked.

3.2 The header: the locality's epoch profile, with percentages

The results header is not just a title. For every locality it summarises the epochs identified in that locality's corpus, with percentages: what share of the classified findings belongs to each epoch. You can see at a glance what kind of place it is — predominantly Roman, medieval, or with a prehistoric presence.

Illustrative example — the epoch profile in the header
Roman38%

The percentages are computed over the already de-duplicated corpus of the search, from the total number of epoch attributions: a finding mentioning two epochs — Dacian and Roman, say — contributes to both, and the printed percentages always add up to 100%. Every value doubles as a filter: press “Roman 38%” and only the Roman findings remain in the list. The chronological strip below the header keeps the absolute number of results per epoch, in chronological order.

Automatic epoch classification

Classification is automatic, by keywords in the title and description of each finding, diacritics-insensitive, across 8 epochs: Prehistory, Bronze Age, Iron Age, Dacian, Roman, Migration period, Medieval, Modern.

  • Roman detection relies on a genuine archaeological lexicon — castrum, legion, oil lamp, burgus, villa, thermae, amphitheatre, colonia, Ulpia, Trajan, “Roman empire”, “Roman Dacia”. The bare words român / română / români (Romanian) do not trigger the Roman epoch, and “Romania” is never confused with Rome.
  • Findings that cannot be placed in any epoch (unspecified period) are dropped from the results, so every card shown carries an epoch. The exceptions are the locality itself (OSM) and the CIMEC/RAN records, which are archaeological by definition.
  • The classification is declared automatic: always check the original source — the link is on every card.

The relevance guard: after aggregation, a result must either mention the locality (diacritics-insensitive) or lie within 30 km of it. The RAN sites around the locality appear with their computed distance (e.g. ~2.0 km) and a direct link to the site record.

Export and persistence

Filtered results can be exported as JSON and CSV (with a BOM, Excel-safe) as detectlab-babel-<locality>.{json,csv}. Results are cached for 30 minutes per language and query, with a force-refresh button.

4. Archaeological potential zones — triangulating the nearby sites

This module uses no artificial intelligence and invents no sites. It starts from a simple observation: known sites are not randomly distributed. Old settlements sit at certain distances from each other, on certain landforms, at certain distances from water. If the analysed area shows a “gap” in that network, surrounded by known sites at comparable distances, then that spot is a statistical candidate for an undiscovered site.

How it is computed

  1. The point on the map (pin) or the map centre is taken, with the chosen radius (1–10 km).
  2. Every known site is loaded from the heritage layers already available (RAN sites, tumuli, site boundaries).
  3. The area is projected to metres and a Delaunay triangulation (Bowyer–Watson) is run over the site coordinates. The resulting triangles are spatially indexed, so any point finds its containing triangle instantly.
  4. The surface is tiled with a regular grid, and every cell is scored on four factors with fixed weights.
  5. Excluded cells (built-up land, too close to a known site, inside a protected perimeter) are tracked separately and drawn red — red means “protected/excluded”, not “interesting”.
Score factors (0–1) and their weights
FactorHow it is computedWeight
Nearby siteshow many sites lie within 1.5 km, normalised by 60.30
Average distancemean distance to the 5 nearest sites, referenced to 3 km0.25

Classification: below 0.25 → the candidate is dropped; 0.25–0.55 → medium potential; above 0.55 → high potential. Thresholds and weights are configurable in the browser, without a redeploy.

Mandatory exclusion rules

  • Built-up land: the candidate must fall on open land according to the UAT mask; the archaeological report additionally requires at least 500 m from any built-up pixel.
  • Site protection: at least 600 m + 100 m buffer (700 m) from any known site point. Polygon sites are sampled along their perimeter every 400 m, so an elongated site cannot be “walked around” by measuring its centre only.
  • Inside perimeters: no candidate may fall inside a site boundary polygon.

What you see on the map

  • Bubbles: a selection of the best cells, each with its own radius, drawn only where there is enough free ground — never overlapping the protection rings.
  • Heat map: the score surface, normalised over the run's own 2nd–98th percentile, so strong zones stand out even when all scores are close.
  • Click a candidate for a pop-up with its classification and score percentage, a 5-star rating (the stars' colour follows the score), the distance to the closest known site (always ≥ 700 m) and the full score breakdown.

The output is a statistical probability derived from the distribution of already-known sites — not a detection. That is exactly why its most useful role is alongside the other modules, inside the archaeological report.

5. LIDAR Scanner — from the AI detection to the validated objective

LiDAR is an airborne laser scan: billions of points measure the ground surface, including under forest. From the point cloud, terrain models (DTM/DSM) and hillshade representations are built, in which man-made shapes — earthen banks, terraces, pits, mounds — become visible.

Stage 1 — the machine-learning model

Over those rasters we ran a machine-learning process: a model trained to recognise relief shapes with a man-made appearance, applied systematically across the covered territory. The output was very large: tens of thousands of raw detections spread across the covered area. At this stage a detection is only a geometric hypothesis — the model does not know what is there, only that the shape breaks the pattern.

Stage 2 — filtering in the database

Raw detections never reach the map directly. They were imported into the DetectLab database and put through a filtering and clean-up process precisely so that the final output contains the most precise objectives possible:

  1. De-duplication — the same shape detected several times (overlapping analysis windows, different confidence thresholds) becomes a single point.
  2. Geometric validation — minimum size, coherent shape, plausible orientation and aspect ratio for a man-made feature.
  3. False-positive removal — forestry roads, modern agricultural terraces, ponds, railway embankments, windthrow mounds, recent trenches, point-cloud processing artefacts.
  4. Grouping — adjacent detections describing the same complex are merged into one objective instead of being left as dozens of isolated points.
  5. Categorisation — every surviving objective gets a type (tumulus, fortification, fort, burgus, rampart, dwelling, trench) or stays marked as an unknown anomaly: a real shape that cannot be classified.
  6. Verification and consolidation — confirmed objectives stay in the database with exact coordinates, ready for spatial queries.

How the scanner is used

  • Pick a point on the map and a radius between 10 and 50 km, then run the scan.
  • Objectives inside the radius are drawn as rings, each with a permanent category tag and its coordinates in the pop-up — useful in the field.
  • Objectives falling inside, or within 600 m of, a known heritage site are not returned: those areas are already documented and legally protected, and overlapping them would only add noise.
  • A result can be annotated. The annotation is used by the archaeological report as a score factor and as an exception to the APM filter.

Unknown anomaly does not mean “worthless”. It means the shape exists in the data, passed the filters, but does not match any known type with certainty — so it stays in the database as a research lead, with the same coordinate precision.

6. The archaeological report — fusing the factors and placing results in their epoch

The archaeological report is the module that combines everything described above. You pick a point on the map and press Run: 5 km² around the point are analysed and the output is a set of 3 ranked locations, drawn as orange polygons, plus a downloadable PDF explaining each result.

The score: the previous factors, weighted

Final classification: high ≥ 0.75, medium ≥ 0.50, otherwise low. Results are ordered with LiDAR-annotated points first, then by score, and must be at least 350 m apart.

Mandatory filters (a candidate must pass all of them)

  1. UAT: the point must be on open land (the opaque red zone of the built-up raster) and at least 500 m from any built-up area.
  2. Known sites: at least 700 m from any site point; polygon sites are sampled along their perimeter, as in the potential module.
  3. APM 2.0: only classes 5 / 4.5 / 4 are accepted.
  4. Exception: a point annotated in the LIDAR Scanner is returned automatically, with its APM component marked unknown.

Placing the resulting locations in their epoch

For each of the 3 locations, the report estimates the epoch from the 3 nearest known sites, by an inverse-distance vote: the closest site weighs the most. The estimate always comes with:

  • the raw dating text from the database — “sec. II-III p.Chr.”, “Hallstatt settlement”, “auxiliary military fort”;
  • the names and distances of the 5 nearest sites, linked to their RAN/CIMEC record;
  • a † marker whenever the dating was derived from the site name rather than a dating field — so you know exactly how firm the information is.

The RAN century notation is parsed: sec. II-III p.Chr., secolul al IV-lea, sec. XII-XIII, sec. II-I î.Chr., mileniul I î.Chr. are mapped onto the same epoch scale the other modules use (Palaeolithic → Modern). “Undetermined” appears only when a record genuinely says nothing.

The PDF

The document is generated locally, with no external libraries: cover → method → one score page per result → a sites and epochs page → figures → sources. The figures are not decoration: the APM potential polygons are drawn from the classified grid of the analysis itself, so they cannot contradict the score. The document language is chosen separately (RO / EN), regardless of the interface language, and diacritics render correctly because the pages are painted on a canvas and embedded as images.

When data is missing, the report does not guess: if the APM tiles cannot be read, every point is rejected, the result is 0 and the PDF button stays hidden, with the reason shown in the status line.

7. Sources, verification and limits

Where the data comes from

The open and institutional sources used by the modules: OpenStreetMap (gazetteer and toponymy), Wikipedia (ro/en), Wikidata, Wikimedia Commons, DBpedia, Archive.org, Europeana, the CIMEC / RAN register for site records, environmental data derived from terrain models, hydrography and geology, plus the validated LiDAR objective database. Every card in the Library of Babel links straight to its source.

What DetectLab does not do

  • It does not invent RAN codes, LMI codes, cultures or site coordinates: where information is missing it stays explicitly missing.
  • It does not transfer information between same-named localities — homonyms are treated as different entities.
  • It guarantees no find: scores are probabilities and field leads, not confirmations.

Legal compliance

DetectLab is a research instrument. Metal detecting in Romania is regulated by Government Ordinance no. 43/2000: owning a detector requires a permit, accessing land requires the owner's consent, and archaeological sites and recorded heritage zones have a special regime. Accidental archaeological finds must be reported within 72 hours and the objects handed over according to the law. Practical, step-by-step details in the Useful information guide.
